# 프로젝트 방향 총정리

> 작성 2026-10-05. 세부 절차는 `docs/runbook/`, 근거 자료는 `docs/reference/`.

## 1. 한 문장

**따릉이 이용자 고장신고를 '이용량 대비 신고율'로 다시 분석해, 부품별 다음 주 신고 건수를 나이브("다음 주 = 지난주")보다 정확히 예측하고, 이를 자전거별 위험도와 정비 대시보드로 확장해 서울시설공단에 제안한다.**

## 2. 왜 다시 하나 — 1차 분석(수업 팀 프로젝트)의 한계

| 1차 분석 | 문제 | 이번에 바꾸는 것 |
|---|---|---|
| 일별 고장 건수를 대여량으로 회귀(OLS) | 대여량이 많으면 고장도 많다는 당연한 관계만 학습. 사실상 "대여량 예측기" | 대여량을 노출(offset)로 내리고 **신고율**을 모델링(음이항 회귀) |
| 나이브 비교 없음 | 1차 LSTM·GRU 모두 네 부품에서 "지난주만큼"을 일관되게 이기지 못함 | 모든 결과표 첫 줄을 나이브로 |
| 미래 날씨에 실측값 사용, 테스트 구간으로 설정 선택 | 성능이 실제보다 좋아 보임 | 학습 2020~23 / 검증 2024 / 테스트 2025~26H1 고정, 날씨는 실제 예보 시나리오 |
| 자기상관 무시 | 유의하다던 기상 변수가 HAC 보정 후 사라짐 | HAC 표준오차 |
| 강수 4단계 범주, 결측을 0으로 | 정보 손실, 기온 0℃와 결측이 섞임 | mm 그대로 + log1p, 결측은 보간 후 표시 |

## 5. 지켜 온 설계 원칙

1. **종속변수는 '고장'이 아니라 '이용자 고장신고'다.** 실제 수거 대수는 신고의 약 2배. 결과는 "신고율·신고 위험도"로 말한다.
2. **신고 건수와 행 수를 구분한다.** 한 행 = 신고×유형. 주 타깃은 신고 건수, 공표치 비교는 행 수.
3. **노출을 먼저 통제한다.** 새 변수마다 "노출의 다른 얼굴인가, 노출 통제 후에도 남는 위험 요인인가"를 묻는다.
4. **나이브를 이겨야 의미가 있다.** 못 이기면 그것도 결과로 쓴다.
5. **테스트 구간은 마지막에 한 번만.**
6. **결정은 사람이, 근거는 숫자로.** 모든 방향 전환은 `decision_log.md`에 근거 수치와 함께.

## 6. 지금까지의 주요 발견 (단계 0)

| 발견 | 수치 | 그래서 바꾼 것 |
|---|---|---|
| 고장신고 API는 날짜 하나에 30일치를 돌려줌 | 07-01 조회 → 07-01~07-31, 8,346행 | 한 번 호출 후 날짜로 거르는 수집 방식 |
| 한 행 = 신고×유형 | 신고당 1.14개 → 행으로 세면 약 14% 과대 | 타깃을 신고 건수로 |
| 공표 통계는 행 기준 | 2024 파일 161,846행 ≈ 공표 162,058 | 비교 기준 명시 |
| 파일과 API가 같은 데이터 | 2026-06, 11,548행 완전 일치 | 과거는 파일, 이후는 API로 이어 붙임 |
| 대여이력과 고장신고 자전거번호 매칭 | 99.87% | 단계 2 진행 |
| 이용거리 품질 양호 | 결측 0%, 기록 누락 약 1% | 노출 = 이동거리, 오류 행은 표시 후 보정 |
| 2021년 신고에는 시각이 없음 | 2021-02~12 시각 0% | 중복 병합 규칙을 행 단위로 |
| 헛대여 신호가 실제로 보임 | 한 시간에 2회+ 헛대여 자전거의 신고 비율 40% vs 정상 5.6%(7.1배, 예비) | 단계 2 핵심 가설의 예비 근거 |

## 6-2. 주요 발견 (단계 1A, 2026-10-05)

| 발견 | 수치 | 그래서 바꾼 것 |
|---|---|---|
| 고장신고 파일은 마지막 날이 통째로 빠진다 | 6일이 0건. API에는 있음(2021-06-30 = 690행) | 보간하지 않고 API 실제 값으로 채움 |
| 요약 파일(이용정보)에 구멍이 많다 | 2016년·2022-05 없음, 4개 파일이 엑셀 줄 수 한계에서 잘림 | 건별 원본(대여이력)에서 다시 합산해 564일 대체 |
| 이동거리는 2020-03 ~ 2021-01-04에 대부분 0으로 기록됐다 | 2020-10 기준 93%가 0 | 단계 0의 "노출 = 이동거리"를 다시 본다. 노출 세 가지를 1B에서 비교 |
| 운영이 멈춘 날이 있다 | 태풍·폭우·시스템 개편으로 3일 전면, 10일 부분 | 보간하지 않고 표시해 제외. 공지 시각을 대여이력으로 확인 |
| 신고율 수준이 계단처럼 바뀐다 | 2018-06 2배(새 앱 5일 뒤), 2020-05 절반, 2021-04 2배, 2025-03 −20% | 레짐 점검. 수준 적응 변수와 학습 구간 재검토(체크포인트 A) |
| 그 변화는 자전거 나이로 설명되지 않는다 | 같은 자전거 묶음이 한 달 만에 2배(2021-04) | 원인을 "신고가 잡히는 정도"의 변화로 보고 외부 자료를 조사. 대부분 원인 미확인으로 남김 |
| 자전거번호가 2020 ~ 2022-02에 새로 붙은 것으로 보인다 | 새 번호가 실제 신규 투입보다 약 18,000개 많음 | 단계 2에서 자전거 나이는 2022-03 이후 번호만 믿는다 |
| 대여 한 건의 길이가 해마다 다르다 | 2020년 29분 → 2023년 이후 20.5분 | 대여건수 기준 신고율을 이용시간 기준과 비교 |

## 7. 이미 알고 있는 패턴 (1차 데이터로 계산, 재확인 예정)

- 요일: 평일 신고율이 주말보다 20~28% 높다. 월요일 초과분은 주말 고장의 신고 지연으로 보인다
- 전날 비: 당일 비는 이용을 줄이지만, 비 온 **다음 날** 신고율이 약 16% 높다
- 기온: U자형. 혹한(≤0℃) +17%, 혹서(≥28℃) +8%
- 부품별 계절성: 타이어는 여름에 거의 3배, 안장은 거의 평평 → 안장은 날씨보다 사용·시간의 함수일 가능성
- 레짐 변화: 2025년 신고 약 30% 감소(대여 약 15% 감소) → 신고율 자체가 내려감

## 8. 한계와 대응

| 한계 | 대응 |
|---|---|
| 정비(수리) 이력 비공개 | 신고 후 대여 공백으로 수리 추정, 공단에 정보 제공 신청 |
| 경로·노면 관측 불가 | 대여·반납 대여소 고도차, 우회율, 속도로 대리 |
| 유사 서비스(RIDEY, 헛대여 경보) 존재 | 차별점: 부품별 수요 예측 + 누적 마모 기반 위험도 |
| 테스트 구간이 다른 레짐(2025 감소) | 건수보다 신고율 설계가 더 중요 |
| 신고율 수준 변화의 원인을 외부 자료로 확인하지 못함(2021-04, 2025-03) | "데이터에서 확인된 구조변화, 원인 미확인"으로 쓰고, 모형은 최근 수준을 따라가게 설계. 공단 문의·정보공개청구 후보로 정리(`docs/reference/10`) |
| 이동거리 기록이 2020 ~ 2022년 일부 기간에 깨짐 | 대여건수·이용시간을 노출 후보로 함께 비교 |

## 9. 자기소개서·면접에서 쓸 수 있는 이야기

- **문제 재정의**: "고장 예측"이 사실은 "대여량 예측"이었다는 진단 → 노출 통제로 재설계
- **데이터 검증 습관**: API·파일의 숨은 함정(30일치 응답, 신고×유형 행, 이름만 .csv인 엑셀)을 숫자로 확인하고 설계를 바꿈
- **가설을 데이터로 가르기**: "새 자전거가 들어와 신고율이 내려갔다"는 가설을 자전거 도입 시기 묶음별 신고율로 확인 → 2020년 하락은 구성 변화였지만 2021년 급등은 같은 자전거 안에서 일어난 변화임을 구분. 공식 자료(단말기만 교체)와 데이터(새 번호 급증)의 어긋남에서 번호 재부여 가능성을 찾음
- **외부 자료와 원자료 교차 검증**: 운영 중단 공지의 시각을 대여이력 시간대별 건수로 확인하고, 공지에 없는 재개 시각과 신고 누락 기간(2023-09 ~ 10)을 데이터에서 찾음
- **정직한 평가**: 나이브 대비 개선율을 첫 줄에, 테스트 구간 한 번만
- **AI 활용 방식**: 반복·검증은 AI에 맡기고 기준·해석·결정은 직접. 결정 로그로 근거를 남김
- **현장 연결**: 정비 인력 60명 동결(1인당 약 750대) 상황에서 "인력 증원 없이 점검 우선순위로 커버리지를 높이는" 도구
