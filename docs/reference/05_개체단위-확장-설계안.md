# 자전거 개체 단위 고장률 분석 — 확장 설계안

작성: 2026-09-12

## 결론
**가능하며, 1차 분석의 "대여량 예측기" 문제를 푸는 정확한 해법.**

- 기존: Y = 일별 고장 건수, X = 일별 대여량 → 구조적으로 `Y ≈ c·X`
- 확장: Y = 자전거 i의 고장 발생, offset = 실제 주행거리 → 대여량이 분모로 내려감
- 남는 질문: *같은 거리를 달렸을 때 무엇이 더 고장나게 하는가* → 언덕, 노면, 우천 주행, 누적 피로, 개체 품질
- 실무 가치: "다음 주 총 400건" → "이 자전거를 예방정비 대상에 올려라"

## 데이터 가용성
| 필요 | 데이터셋 | 상태 |
|---|---|---|
| 고장 이력 (자전거번호·등록일시·고장구분) | 서울 열린데이터광장 OA-15644 | 자전거번호 포함 확인 |
| 대여 이력 (자전거번호·대여/반납 대여소·이용시간·이용거리) | OA-15182, 2015~, 반기별 | "자전거별 대여이력" 명시, 컬럼은 파일로 확인 필요 |

## 네 가지 난관

### 1. 규모
연 2,880만 건 × 다년 = 1억 행 이상. R data.frame 불가.
- 도구: DuckDB + Parquet (또는 polars)
- **코호트 표본 권장**: 2021년 첫 등장 자전거 3,000대를 2023년까지 추적. 검정력 충분, 계산량 1/100, 좌측절단 동시 해결.

### 2. 경로 식별 불가 (가장 중요)
데이터는 O-D만 제공. "험한 길을 몇 번 지났나"는 원리적으로 식별 불가 → 프록시로 재정의(이것이 방법론적 기여).

식별 가능한 대리변수:
- **순 고도차** = 반납소 고도 − 대여소 고도 (진짜 식별됨). 등판→체인/페달, 내리막→브레이크/타이어로 부품별 가설이 선명.
- **우회율** = 이용거리 ÷ 직선거리(haversine)
- **평균 속도** = 이용거리 ÷ 이용시간
- **O-D 구간 경사 프로파일** = DEM 샘플링한 최대 경사·총 상승고도 (실제 경로는 아니나 "최소 이만큼은 올라야 한다"는 하한)

**함정**: 왕복 대여(A→A)는 순 고도차 0인데 거리가 김 → 순 고도차만 쓰면 왕복이 전부 '평지'. 우회율·속도 병용 + 왕복 더미 필수.

**검증**: 자치구별 평균 경사(관악·종로 vs 강서·송파)와 프록시가 일치하는지 확인.

### 3. 생존분석 문제 (회귀 아님)
단순 (고장수 ÷ 대여수)는 좌측절단(첫 등장일 ≠ 투입일), 우측절단, 재발 구조를 모두 놓침.

- **1단계(권장 출발점)**: 자전거 × 월 패널 + 음이항 GLM, `offset = log(월 주행거리)`, 자전거 고정효과
- **2단계(고도화)**: Andersen–Gill 재발사건 Cox (`survival::coxph` + `cluster(bike_id)`), 시간가변 공변량. 부품별은 경쟁위험.

**선행연구 연결**: 이미 인용한 Grau-Escolano et al. (2024) 바르셀로나 Bicing이 정확히 이 설계. 방법론 차용 + **"서울 + 지형(고도) 변수"**로 차별화 → *"선행연구는 개체 수명을 예측했으나 지형 노출을 고려하지 않았다"*

### 4. 고장신고 데이터 성질
- 신고 기반 ≠ 고장 기반. offset이 부분적으로만 통제
- 중복 신고 → *동일 자전거 + 동일 유형 + 48시간 이내*를 1건 병합 규칙 명시
- 정비 완료 기록 없음 → 신고 후 대여이력 끊긴 기간을 '수리 중'으로 추정, 이 gap이 고장 심각도 파생변수
- **자전거번호 안정성이 1순위 확인 사항**: 2020~2022 LCD→QR 단말기 교체 시 번호 체계 변경·재사용 가능성. 깨지면 설계 전체 무너짐.

## 진행 순서

**Phase 0 — 조인 검증 (반나절, 여기서 중단 여부 결정)**
반기 파일 1개 + 고장신고 1년치로:
- 자전거번호 포맷 일치 여부 (`SPB-xxxxx` 접두사·자릿수)
- **고장신고 자전거번호의 대여이력 매칭률** — 90%↑ 진행 / 70%↓ 중단
- 연도별 파일 스키마 일관성
- 이용거리 컬럼 존재 및 0·결측 비율

**Phase 1 — 지형 테이블 (2~3일)**
대여소 좌표 + DEM 고도 조인. **실제 등장 O-D 쌍만** 순 고도차·직선거리·경사 프로파일 계산해 룩업 테이블화.

**Phase 2 — 자전거 × 월 패널 (1~2주, 작업량 70%)**
DuckDB 집계 컬럼:
- 노출: 대여 횟수, 총 주행거리, 총 이용시간
- 지형: 누적 상승/하강고도, 평균·최대 우회율, 평균 속도, 왕복 비율
- 기상 노출: 우천일 주행 횟수·거리, 혹서(30℃↑)·혹한(0℃↓)·적설일 주행
- 누적: 투입 이후 총 주행거리·총 상승고도, 직전 고장 이후 경과 거리
- 결과: 해당 월 부품별 고장 신고 건수

**Phase 3 — 모형 (3~5일)**
음이항 GLM, `offset = log(주행거리)`, 부품별 5개 모형. 여기서 이미 결과 나옴.

**Phase 4 — 생존분석 (선택, 1~2주)**
Andersen–Gill 재발사건 모형.

## 기간·리스크
- Phase 0~3 혼자서 **3~5주** (데이터 엔지니어링 70% / 모델링 20% / 해석 10%)
- 리스크 ①: 자전거번호 조인 실패 → Phase 0에서 반나절 만에 판명
- 리스크 ②: 대여이력 연도별 스키마 불일치 (컬럼명·인코딩 CP949/UTF-8·날짜 포맷)
- **범위 축소 시 기간이 아니라 자전거 대수를 줄일 것.** 3,000대 × 3년 > 45,000대 × 1년 (개체 내 누적 피로 변동 관측이 핵심)
