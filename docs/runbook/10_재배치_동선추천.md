## R1 수집

- 대여소 실시간 대수(`bikeList`): 한 번에 1,000곳, 약 2,800곳 → 호출 3번. 표본 한 번 받아 대여소 수·열·걸린 시간 확인 → 하루 행 수·저장 크기 추정
- TOPIS(`TrafficInfo`, XML만, 링크 하나에 호출 한 번): 전체 링크 목록을 받는 방법 찾기(`RoadInfo` → 도로별 링크), 링크 수 세기 → 근무조 15분 간격의 하루 호출 수 계산 → 호출 한도 확인
- `[결정]` 호출 한도에 걸리면 도로 속도 간격을 30분으로 내릴지 → 자동 전환(결정 로그 2026-11-01)

> 결과(2026-11-01): 수집기 두 개를 만들고 맥 운영 DB에 한 번씩 돌렸다. 대여소 2,721곳 약 1초, 도로 링크 5,162/5,337개
> (나머지는 자료 없음) 1분 30초. 다시 돌려도 중복 없음. 서버 예약은 `deploy/setup.sh`에 넣었고 서버 등록은 사람이 한다.
> 상세는 `docs/notes/09`, 작업표는 `docs/pipeline.md`.

## R2 도로망·이동시간

- 서울 차량 도로망(OpenStreetMap) → 대여소를 가까운 도로 지점에 붙임 → 구역마다 대여소 사이 이동시간 표
- TOPIS 링크(꼭짓점 좌표 `LinkVerInfo`, GRS80 TM)를 OSM 도로에 겹쳐 붙이고 그 시각의 속도로 보정
- 확인: 몇 쌍을 사람이 지도 앱 경로 시간과 비교

> 결과(2026-11-02): OSM은 Overpass가 거절해 Geofabrik 파일에서 잘랐다(`road_graph.py`). TOPIS는 큰길 길이의 50 ~ 63%에 붙고
> 골목엔 거의 안 붙어, 붙은 비율이 낮은 등급은 등급 중앙값 대신 기본 속도를 쓰게 바꿨다(런북에 없던 규칙). N04에서 도로 시간은 팀 가정의
> 약 0.74배. 기본 속도·등급 기준은 임시값이고 `[결정]` 대상. 상세 `docs/notes/09`.

## R3 재배치 현황

- 역산: 반납한 곳 ≠ 다음 대여한 곳. 같은 출발·도착을 여러 대가 함께 밟았으면 트럭 재배치, 혼자이고 48시간 넘게 쉬었으면 수리 다녀옴(표본 확인 2026-11-01, `docs/notes/09`)
- 실시간 대수 5분 간격의 급변(트럭이 온 순간)으로 당일 현황 보강

## R4 부족·과잉 예측

- 대여소 × 시간대마다 대여 수와 반납 수를 따로 예측(⑥에 필요). 먼저 나이브(같은 요일·시간대 평균), 그다음 모형
- 빈 대여소일 때 못 빌린 수요는 기록에 없다(억눌린 수요) → 보정 방법 `[결정]`
- 지금 n대일 때 3시간 실패 대여·실패 반납 기대 건수 표 → 목표 대수

## R5 동선

- OR-Tools: 구역마다 트럭별 정차 순서·싣고 내릴 대수. 목표 = 옮긴 뒤 줄어드는 실패 건수 − 이동시간 비용
- `[결정]` 이동시간 1분과 실패 1건을 어떻게 바꿔 셀지(가중치)

## R6 재생기·검증

- 1분 단위로 과거 근무조를 다시 돌린다: 대여·반납, 트럭 이동(그 시각 도로 속도), 억눌린 수요 보정, 수요 다시 뽑기 여러 번
- 비교: 재배치 없음 / ① / ④ / 실제 트럭 재배치(역산 재생) / ⑥
- `[결정]` 지표와 통과 기준을 결과를 보기 전에 정한다(후보: 실패 대여, 실패 반납, 트럭 km)
