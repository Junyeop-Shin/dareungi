### 권장 순서

1. 단계 3 MVP 완성(대시보드 배포 + 2주 무중단 수집)
2. 공단 일반제안 제출. 시범 운영을 요청한다
3. 같은 결과물로 다음 해 경진대회 시각화 또는 창업 부문 준비(공고가 나오면 조건 재확인)
4. 상상대로 서울은 시민 관점(자전거 조회 + 안전) 버전으로 선택

일정 예시: 2026년 10월 단계 1 → 11~12월 단계 2 → 2027년 1월 단계 3 → 2월 공단 제안 → 봄 경진대회.

## 3C-3. 본문 구조와 쓸 내용

### 1. 문제 (숫자로)

| 숫자 | 출처 |
|---|---|
| 고장신고 162,058건(2024) → 112,970건(2025) → 71,236건(2026년 1~8월) | 헤럴드경제 2026-09-19(공단 자료) |
| 실제 수거는 접수의 약 2배(이수센터) | 헤럴드경제 2026-09-19 |
| "앱에는 정상으로 표시돼도 브레이크·체인·안장이 고장 난 경우가 많다" | 아이뉴스24 2025-06-25 |
| 정비 정원 60명이 2022년 이후 동결, 1인당 약 750대 | 아이뉴스24 2025-06-25 |
| 서울 최근 3년 안전사고 2,068건 중 138건이 자전거 하자 | 더팩트 2025-09-06(이경숙 시의원 자료) |
| 전국 공영자전거 사고 2,323건 중 결함 관련 237건(2024.1~2026.6), 점검·회수 기준을 국가가 정하는 법안 발의(2026-08-13) | 뉴스토마토 2026-08-13 |
| 운영 적자 109억(2023) → 127억(2024) | 더팩트 2025-09-06 |

숫자는 제출 직전에 최신 자료로 다시 확인한다.

### 2. 제안

"인력을 늘리지 않고, **어디를 먼저 볼지**와 **무엇을 얼마나 준비할지**를 데이터로 정한다."
- 화면 ① 부품·인력 주간 예측
- 화면 ② 점검 우선순위 목록 + 헛대여 경보
- (선택) 화면 ③ 시민 조회

### 3. 근거

- **검증 결과:** 04·06의 **테스트 구간** 숫자만 쓴다. 검증 구간 숫자를 성능이라고 쓰지 않는다
  - 부품별 주간 예측: 나이브(지난주만큼) 대비 오차 감소율, 80% 구간 적중률
  - 점검 우선순위: 위험 상위 1,000대의 다음 주 신고 비율 vs '많이 탄 순서' 기준
  - 헛대여 경보: 경보 후 7일 안 신고 비율, 선행 시간
- **해외 사례**
  - Citi Bike(뉴욕): 모든 자전거 45일 안에 점검·청소, 결함은 48시간(도크 신고)·96시간 안에 해결을 계약 서비스 기준(SLA)으로 매달 공개(2026년 6월 보고서)
  - Ecobici(멕시코시티): 2026년 5월 브레이크·타이어·체인 부품 부족으로 1,000대 넘게 운행 불가 → 부품 수요 예측의 필요
  - 바르셀로나 Bicing 연구: 이용 기록으로 부품 수명을 예측(Grau-Escolano et al. 2024, *EPJ Data Science* 13:48)
- **공단의 방향과 맞음:** 공단은 도로·교량 내부 상태 예측 알고리즘 특허 출원과 자산관리 국제표준(ISO 55001)을 추진 중이다(뉴스핌 2026-09-11). 따릉이에 같은 '예측 기반 자산관리'를 적용하는 제안으로 설명한다

### 4. 운영 방법 (공단의 주간 흐름에 맞춘다)

| 언제 | 누가 | 무엇을 |
|---|---|---|
| 매주 월요일 오전 | 정비 관리자 | 화면 ①로 부품 발주·인력 배치 확인 |
| 매일 아침 | 순회 정비 | 화면 ②에서 담당 자치구 상위 N대 CSV → 동선 |
| 매일 | 현장 | 점검 결과(고장 있음/없음, 부품)를 간단히 기록 → **모델 개선 자료** |

### 5. 시범 운영 제안

- 범위: 정비센터 1곳(예: 이수센터 담당 구역), 8주
- 방식: 담당 구역 '점검 권장' 목록 상위 N대를 주 1~2회 순회 점검, 결과 기록
- 성과지표(KPI)

  | 지표 | 정의 | 기준선 |
  |---|---|---|
  | 목록 적중률 | 목록에서 점검한 자전거 중 실제 결함 발견 비율 | 무작위·'많이 탄 순서' 점검 |
  | 선제 수거 | 신고 전에 수거된 결함 자전거 수 | 시범 전 같은 기간 |
  | 신고→수거 시간 | 중앙값 | 시범 전 |
  | 부품 긴급 발주·결품 횟수 | 주당 | 시범 전 |
  | 예측 오차 | 부품별 주간 MAE% | 나이브 |

- **현장 점검 결과는 실제 고장 정답이다.** 신고 기반 라벨의 가장 큰 한계를 여기서 처음으로 넘을 수 있다고 강조한다

### 6. 공단에 요청하는 것

1. 정비 이력(자전거번호, 입고·완료 일시, 수리·교체 부품, 정비센터) — 수리 후 위험 초기화, 부품별 수명 분석에 필요
2. 정비센터별 담당 구역(대여소 목록) — 센터 단위 예측
3. 부품 재고·발주 이력 — 권장 확보 수량의 실제 검증
4. 시범 운영 기간의 현장 점검 기록

### 7. 한계와 대응

| 한계 | 대응 |
|---|---|
| 라벨이 '신고'다(실제 고장보다 적다) | 시범 운영 점검 기록, 정비 이력 확보 |
| 수리 기록이 없다 | 신고 후 대여 공백으로 추정, 정비 이력 받으면 교체 |
| 경로·노면을 모른다 | 대여소 간 고도차·우회율로 근사 |
| 체인가드·8단 기어 등 설계 변경 | 개입 변수 + 반기 재학습 |
| 공식 서비스가 아니다 | 모든 화면에 고지. 공단 채택 시 이관 가능 |

### 8. 부록

방법 요약, 데이터 출처(공공누리 제1유형 출처 표시), 모델 카드(06), 코드 저장소 주소, 재현 방법.

## 3C-4. 예상 질문과 답변 초안

| 질문 | 답변 방향 |
|---|---|
| 앱 신고로 충분하지 않나? | 실제 수거는 신고의 약 2배다. 신고되지 않는 고장을 신고 전에 찾는 것이 목적이다 |
| 정확도는 어느 정도인가? | 테스트 구간 숫자로 답한다(나이브 대비 +○%, 상위 1,000대 적중 ○%). 과장하지 않는다 |
| 개인정보 문제는? | 공개 데이터만 쓰고, 이용자 속성·개별 대여 기록은 화면에 보이지 않는다(집계만) |
| 운영 부담은? | 자동 수집·갱신. 현장은 목록을 받아 점검하고 결과만 기록한다 |
| 비슷한 민간 서비스(RIDEY)와 뭐가 다른가? | 그쪽은 '지금 고장인가' 경보. 이쪽은 누적 마모 기반 부품별 위험과 정비·부품 수요 예측. 헛대여 신호는 서울 신고 데이터로 검증까지 했다 |
| 비용은? | 공개 데이터와 소형 서버 수준. 공단 시스템과 연동하면 그 비용은 별도 |
| 자전거 설계가 바뀌면? | 개입 변수로 반영하고 반기마다 재학습, 성능이 나아질 때만 교체 |
